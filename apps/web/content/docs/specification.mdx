## Abstract

This specification defines a standardized message format and Ed25519 verification process that lets Solana wallet owners authenticate with off-chain services without on-chain transactions.

## Motivation

Solana wallets are widely deployed, yet no standard exists for using them as authentication credentials. Ad-hoc implementations lead to:

- Inconsistent user experiences
- Security vulnerabilities
- Lack of interoperability

This specification addresses these issues with a secure, human-readable message format and verification process.

## Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Additional terms:

- **Wallet**: A cryptographic keypair capable of signing messages using Ed25519
- **Relying Party**: The service requesting authentication
- **Message**: The human-readable string presented to the user for signing

## Message Format

A SIWS message MUST conform to the following structure:

```txt
${domain} wants you to sign in with your Solana account:
${address}

${statement}

URI: ${uri}
Version: ${version}
Nonce: ${nonce}
Issued At: ${issuedAt}
Expiration Time: ${expirationTime}
Not Before: ${notBefore}
Request ID: ${requestId}
Cluster: ${cluster}
Resources:
- ${resources[0]}
- ${resources[1]}
- ...
```

## Required Fields

| Field | Description | Format |
|-------|-------------|--------|
| `domain` | RFC 3986 authority requesting authentication | `authority` per RFC 3986 |
| `address` | Solana wallet address | Base58-encoded Ed25519 public key |
| `uri` | RFC 3986 URI identifying the authentication target | `URI` per RFC 3986 |
| `version` | SIWS specification version | `1` |
| `nonce` | Randomized token for replay protection | Alphanumeric, >=8 characters |
| `issuedAt` | Message creation timestamp | ISO 8601 datetime |
| `cluster` | Solana network identifier | `mainnet-beta` \| `devnet` \| `testnet` |

## Optional Fields

| Field | Description | Format |
|-------|-------------|--------|
| `statement` | Human-readable purpose description | Printable ASCII (`%x20-7E`), single line |
| `expirationTime` | Message expiration timestamp | ISO 8601 datetime |
| `notBefore` | Message validity start timestamp | ISO 8601 datetime |
| `requestId` | Application-specific request identifier | Printable ASCII (`%x20-7E`) |
| `resources` | Resources being authorized | Array of RFC 3986 URIs |

## Field Definitions

### domain

RFC 3986 authority matching the requesting origin. MUST NOT include a scheme or path. Relying parties MUST reject mismatched domains.

### address

Base58-encoded Ed25519 public key. It MUST decode to exactly 32 bytes (32-44 characters; almost always 43-44). The signature MUST be verified against this key. If the relying party also receives a claimed address or public key out of band, it MUST be equal to `address`.

### uri

Valid RFC 3986 URI. SHOULD match the endpoint receiving the authentication request.

### version

MUST be `1` for this specification.

### nonce

At least 8 alphanumeric characters from a CSPRNG. Relying parties MUST:

1. Generate a unique nonce per authentication attempt
2. Store nonces server-side with an expiration time
3. Reject unknown, expired, or previously used nonces
4. Invalidate nonces after successful verification

**Recommendation**: Use >=16 bytes of randomness, Base58 or hex encoded.

### issuedAt

ISO 8601 datetime in UTC: `YYYY-MM-DDTHH:mm:ss[.sss]Z`. It MUST name a real calendar instant (e.g. `2024-02-30`, hour `24` and minute `60` are invalid). The same rule applies to `expirationTime` and `notBefore`.

### statement

OPTIONAL. MUST NOT contain newline characters. SHOULD describe the authentication purpose.

### expirationTime

OPTIONAL. Relying parties MUST reject messages at or after this time.

**Recommendation**: 5-15 minutes from `issuedAt`.

### notBefore

OPTIONAL. Relying parties MUST reject messages strictly before this time.

### cluster

REQUIRED. One of `mainnet-beta`, `devnet`, `testnet`. Relying parties MUST validate to prevent cross-cluster replay.

### resources

OPTIONAL. Each resource MUST be a valid RFC 3986 URI.

## Signature Verification

Solana uses Ed25519 for message signing. Verification MUST proceed as follows:

1. Parse the message string strictly (see [Canonical Form](#canonical-form)) and reject it if it is not canonical
2. If a public key was supplied separately, reject it unless it equals the message `address`
3. Encode the message string as UTF-8 bytes
4. Decode the signature from Base58 (64 bytes)
5. Decode the `address` from Base58 (32 bytes)
6. Verify using Ed25519: `ed25519.verify(signature, message, address)`

## Message Grammar

The message format is defined using ABNF ([RFC 5234](https://www.rfc-editor.org/rfc/rfc5234)):

```abnf
siws-message    = domain-line LF address-line LF LF
                  [ statement-line LF LF ]
                  field-lines

domain-line     = domain " wants you to sign in with your Solana account:"
address-line    = address
statement-line  = statement

field-lines     = uri-field LF version-field LF nonce-field LF
                  issued-at-field
                  [ LF expiration-field ]
                  [ LF not-before-field ]
                  [ LF request-id-field ]
                  LF cluster-field
                  [ LF resources-field ]

uri-field       = "URI: " uri
version-field   = "Version: " version
nonce-field     = "Nonce: " nonce
issued-at-field = "Issued At: " iso8601-datetime
expiration-field = "Expiration Time: " iso8601-datetime
not-before-field = "Not Before: " iso8601-datetime
request-id-field = "Request ID: " request-id
cluster-field   = "Cluster: " cluster
resources-field = "Resources:" 1*( LF "- " uri )

domain          = authority                    ; RFC 3986
address         = 32*44BASE58CHAR            ; MUST decode to 32 bytes
uri             = URI                          ; RFC 3986
version         = "1"
nonce           = 8*ALPHANUM
statement       = 1*( %x20-7E )                ; printable ASCII, no newlines
request-id      = 1*( %x20-7E )
cluster         = "mainnet-beta" / "devnet" / "testnet"
iso8601-datetime = ; ISO 8601 datetime with Z suffix

ALPHANUM        = ALPHA / DIGIT
BASE58CHAR      = %x31-39 / %x41-48 / %x4A-4E / %x50-5A / %x61-6B / %x6D-7A
LF              = %x0A
```

The message ends immediately after the last field or resource. There is no trailing `LF`.

## Canonical Form

Signatures cover the exact message bytes, so a verifier MUST accept only one textual form per set of fields. A message is canonical when it matches the grammar above exactly. Verifiers MUST reject (with a parse error) any message that:

- uses `CR` or `CRLF` line endings, or ends with a trailing `LF`
- contains fields out of the order given in the grammar
- repeats a field (for example two `Nonce:` lines)
- contains unknown fields or lines that match no rule
- has extra or missing blank lines, or a field separator other than `": "`
- has a statement that looks like a field line (for example `URI: ...`)
- has a `Resources:` line with no resource entries

A simple way to enforce this is to parse the message, serialize the parsed fields back into a string, and reject the message unless the two strings are identical. `@siws/core` does this.

## Security Considerations

### Replay Attacks

Captured signatures reused for unauthorized authentication. Single-use nonces MUST be enforced with expiration (RECOMMENDED: 5 minutes). `expirationTime` provides defense in depth. A verifier that does not compare the message nonce with a server-issued nonce has no replay protection.

### Cross-Site Request Forgery

Signatures obtained from one site used on another. `domain` MUST be verified server-side and `uri` binds authentication to a specific endpoint. Relying parties MUST reject domain/URI mismatches.

### Account Substitution

A message naming one address can be signed by a different key. Verifiers MUST verify the signature against the message `address`, and MUST reject the message if a separately supplied public key or claimed address differs from it. Otherwise an attacker could sign a message naming a victim's address with their own key.

### Parser Ambiguity

If parsers ignore unknown lines or let a repeated field override an earlier one, the fields a wallet displays and the fields a server acts on can differ (for example `Nonce: a` followed by `Nonce: b`). Verifiers MUST accept only the [canonical form](#canonical-form).

### Phishing

Users deceived into signing messages for malicious sites. Wallets SHOULD display the complete message before signing and warn on unfamiliar domains. `domain` and `statement` help users identify the requesting party.

### Nonce Compromise

Leaked or predicted nonces enable replay attacks. Generate nonces using CSPRNG, store server-side only, bind to session or client identifiers, and enforce expiration.

## Test Vectors

### Vector 1: Minimal Message

```
example.com wants you to sign in with your Solana account:
7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU

Sign in to Example

URI: https://example.com/auth
Version: 1
Nonce: k8sj2n4b
Issued At: 2024-01-15T12:00:00Z
Cluster: mainnet-beta
```

### Vector 2: Complete Message

```
app.example.com wants you to sign in with your Solana account:
7xKXtg2CW87d97TXJSDpbD5jBkheTqA83TZRuJosgAsU

Access your dashboard and manage settings.

URI: https://app.example.com/api/auth
Version: 1
Nonce: f7k2m9p4x1
Issued At: 2024-01-15T12:00:00.000Z
Expiration Time: 2024-01-15T12:10:00.000Z
Not Before: 2024-01-15T12:00:00.000Z
Request ID: req_abc123
Cluster: mainnet-beta
Resources:
- https://app.example.com/api/profile
- https://app.example.com/api/settings
```
